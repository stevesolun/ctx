# Spec format

Adapt this structure to the work. Omit sections that add no information.

## Problem

Describe the current problem from the user's perspective and why it matters.

## Desired behavior

Describe the observable outcome, relevant success and failure paths, and
important edge cases. Use user stories only when they clarify distinct actors or
workflows.

## Acceptance criteria

List concrete, independently verifiable outcomes. Prefer behavioral contracts
over implementation steps.

## Decisions and constraints

Record decisions already made, including relevant interfaces, data contracts,
compatibility requirements, architectural constraints, and test seams. Mark
inferences and unresolved decisions plainly.

## Out of scope

Name adjacent work that could otherwise be mistaken for part of the request.

## References

Link source issues, prototypes, existing tests, ADRs, or code artifacts that
carry important context.
